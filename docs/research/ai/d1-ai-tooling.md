# D1: Owner's AI tooling repos vs the Axiom AI layer (read-only, 2026-11-10)

Method: read READMEs/docs/package.json/selected source and git metadata only. Nothing run. Claims below are from code/docs; "unverified" marks anything I did not confirm. I saw no secrets. Note: aisskills HANDOFF.md says two npm tokens were pasted in chat (not in repo) and must be revoked; ~/.config/aiskills-bench-github-token exists (not opened). CodeAtlas/.mcp.json points at a ContextGit-pr-7 venv path (stale config, harmless).

Common: all are TypeScript/Node (aisskills, CodeAtlas, ModelChecker) or Python+Electron (ContextGit). Axiom image is small and "no new daemon without ADR"; Node (>=20, CodeAtlas >=22.13) or Python (>=3.11, FastAPI+uvicorn) runtimes are real weight. Everything is by the same owner, so relicensing/contribution is not a blocker (Apache-2.0 for Axiom; MIT and Apache-2.0 are both compatible).

## 1. aisskills (npm @prof-bilal/aiskills 0.2.0-beta.2)
- What it does: local CLI + MCP gateway holding a catalog of skills/skill packs/MCP tools. Installs from local path or GitHub, snapshots and scans WITHOUT executing, requires user approval + per-project enablement, writes a lockfile with content and runtime-policy hashes. Router selects only task-relevant skills; MCP compact tools (`use_skills`, `load_skill`, `search_tools`, `call_capability`, `discover_capabilities` under --full) start approved MCP gateways lazily, behind Warden (separate sandbox binary, ShieldCI repo, not in my scope; unverified here). Also: `aiskills hook` (Claude Code UserPromptSubmit), `aiskills guard` (PreToolUse deny: non-allowed network hosts, secret paths, writes outside project, sudo; string-level, admits misses obfuscated commands), reply guard (blocks secrets in final reply), untrusted-skill wrapping with random boundary, Rule-of-Two sessions, hidden-content scanner. Orchestration: `CoreRuntime` plans, routes native vs optional Smurf engine (external repo, NO LICENSE found, redistribution blocked per its own doc), accepted work merges to an integration branch never the user's checkout. SQLite memory + guarded browser reference store.
- Maturity: 86+ commits, 2026-10-22 to 2026-11-09 (very active), ~4.2k LOC in packages (dense one-line style), 18 test files, handoff reports 117 tests / 112 pass / 5 skipped (live Warden). npm beta published; newest features (use_skills, hook, guard) unreleased and 8 commits unpushed. CI + publish workflows. Benchmarks dir (routing, security arms).
- Stack: Node>=20, pnpm 12, TS, better-sqlite3 (native module, rebuild pain noted), playwright-core, yaml, @modelcontextprotocol/sdk. Needs Warden binary for executable tool isolation, bubblewrap in some API-mode checks. License MIT.
- Interfaces: CLI (`aiskills init/add/install/skills/packs/run/mcp/hook/guard`), MCP stdio server, SDK package (declarative extension defs), files: skill manifest, lockfile, catalog in SQLite.
- Skill/permission/verification model: manifest `schema_version:1, id, name, description, version, category, capabilities[], activation.triggers[], requires.permissions[] (e.g. repository.read), access {network:[hosts], secrets:bool}, recommended_tools, dependencies.skills, checks[], risk_level, compatible_agents, context`. Accepts native YAML AND Agent Skills Markdown (SKILL.md) on import (LAUNCH_READINESS), so it is a superset/runtime around the Agent Skills spec, not a competing format. Permissions are declarative metadata reviewed at install, pinned by hash in lockfile, rechecked at each executable call. Verification = evidence records + `checks` (exact host-approved commands) + independent reviewer in orchestration; "worker output alone never establishes completion".
- Axiom view:
  1. Fit: closest conceptual match to Axiom's planned agent definition (declarative metadata + prompt, no code, deny-by-default, capability grants). Its manifest fields map almost 1:1 to what docs/ai/AGENT_SYSTEM.md wants (frontmatter, grants, deterministic checks). Lockfile+hash+recheck is a pattern Axiom should copy. Progressive disclosure/`use_skills` is exactly "avoid model calls / small context". Hook+guard show what a deny layer looks like for third-party agent CLIs.
  2. Needs vs duplicates: Axiom needs the manifest schema, scanner rules (hidden content, unsafe exec phrases), untrusted-wrapping, lockfile design, routing-by-task. It duplicates: MCP gateway, Warden sandbox (Axiom would use its own typed-action broker + bubblewrap/systemd), CLI agent adapters (Codex/Claude Code/OpenCode runners), Smurf bridge.
  3. Cost/risk: Node + native sqlite module + playwright on image; guard is string-level (Axiom rule: typed actions, not shell filtering) so it cannot be the enforcement boundary; Smurf has no license; permissions vocabulary is coarse (repository.read, network hosts, secrets bool) versus Axiom's S5 typed-action/sensitivity model; runs as user, no root assumption (good). Network: GitHub installs, HTTPS reference fetch (opt-in).
  4. Verdict: PORT-CONCEPT (manifest + lockfile + scanner + untrusted wrapper + progressive routing). Optionally RECOMMEND-ONLY as a developer-side companion for Claude Code/Codex users on Axiom (works unmodified). Do not bundle Node gateway as the Axiom skill runtime; reimplement a small subset in the Axiom services language and keep manifest compatibility so the same skill packs load in both.

## 2. aiskills-library
- What it does: content only. 3 categories (core, grind, orchestration) of Agent Skills (`SKILL.md` with YAML frontmatter: name, description, license, compatibility; sections Activation / Required context / Workflow...), 6 playbooks (bug-fix, documentation, feature-delivery, release, research, security-review), templates, references, `skills-index.json`, `evaluation-cases.json`, `sources.json`. Node scripts: build-index, validate-skills, check-links, check-evaluation, export-agent-views (.agents/skills and .claude/skills views).
- Maturity: 3 commits (2026-10-25 to 2026-10-29), tiny, no CI seen, no releases. License MIT. Runtime: none (Markdown); validation scripts need Node.
- Interfaces: file format = open Agent Skills spec; index JSON.
- Axiom view: (1) ship as data: seed library of default Jarvis skills/lessons and playbooks (instructions only, so passes "no executable user content" rule S9); format = the file format Axiom's agent definition already intends. (2) Needs: skill-router, workflow-coordinator, researcher-style skills as examples; evaluation-cases.json as seed eval cases. Duplicates nothing. (3) Cost ~0; risk: quality is unproven (3 commits, no measured effect), content is original per sources.json. (4) Verdict: BUNDLE (as data, after a quality pass and measurement via ModelChecker-style cases). 

## 3. CodeAtlas / RepoSpine (repo CodeAtlas; `atlas` CLI, npm repospine-cli, 0.7.0-beta.1 candidate, NOT published)
- What it does: scans a repo, SHA-256 change detection, parses (ts-morph for TS/JS; tree-sitter WASM for Python, Go, Java, C#, Rust), builds dependency/symbol graph, stores in SQLite (`node:sqlite`) under `<repo>/.codeatlas/`, serves ranked search and budgeted, deny-filtered `ContextPackage`/WorkPacket via Context SDK, CLI, MCP stdio (context profile + opt-in 7-tool proof profile), VS Code extension. Also: 13 first-party Skills, a tool registry/installer with trust assessor, agent sessions, usage/credit tracking, and a "proof system": change sessions, explicit obligations, revision-bound evidence, invalidation, completion receipts ("proven" only means represented checks pass; model statements cannot supply evidence), experimental goal-satisfaction layer. AI is optional; facts are deterministic.
- Maturity: 136 commits 2026-09-12 to 2026-11-03, ~99k LOC TS, 173 test files, CI + goal-gate workflows, extensive docs and audits. Published `codeatlas-cli` earlier; rename to repospine in flight. Node>=22.13. MIT.
- Evidence on small models: pilot benchmark (opencode/deepseek-v4.1-flash-free, 3 repos x 12 tasks x 2 reps x 2 arms = 48 runs): solved 22/24 baseline vs 23/24 with CodeAtlas WorkPacket; repair 83.3% vs 91.7% (1 win/0 loss/11 ties, CI 0 to 0.25); agent time 183.7s vs 126.9s (CI excludes zero narrowly). Report itself says directional only, wide CIs, not significance; README says live-agent quality gains unmeasured. So: plausible token/time saver, quality effect NOT established. The tasks were already easy for the model (baseline 92%).
- Could it be "big models teach small models"? No, not directly. It is a retrieval/context-packing and verification mechanism: it makes ANY model see better, bounded, fresh code context, and its proof receipts verify claims. It does not distil, fine-tune, or transfer reasoning. It fits as the "context/RAG scaffold" half of lessons (a lesson can say "call context_for(task) first"), and its proof/receipt layer maps to Axiom's verify-then-claim rule. It is code-centric (repos), whereas Axiom lessons also cover OS/desktop tasks.
- Interfaces: `atlas`/`repospine` CLI, MCP (stdio), SDK, files `.codeatlas/context.db`, SKILL.md files, VS Code ext.
- Axiom view: (1) Optional bundled app/service for the Developer Hub (Phase 6 already has a Developer Hub): project index on demand, launched per-session over MCP stdio (no resident daemon unless `watch`). As a library it is too big to embed. (2) Needs: the budgeted/deny-filtered context package idea, receipt/obligation model, small-model quality profiles (commit "token and small-model quality profiles"). Duplicates: skills registry, tool installer/configurator (overlaps aisskills and Axiom's own policy), usage tracking, agent sessions, a TUI/VS Code, ChatGPT plugin. Scope creep is large; ~99k LOC. (3) Cost: Node>=22.13 plus WASM grammars plus ts-morph on image (tens to hundreds of MB with node_modules; unverified), heavy for default install; tool installer that installs third-party tools needs the Phase 7 helper path, not self-install; proof profile "runs host-approved verification actions" (fine if approvals go through Axiom's broker). Network none by default. Writes only under repo `.codeatlas/`. Lowest-risk of the bunch privilege-wise. (4) Verdict: RECOMMEND-ONLY (offer as an optional Developer Hub install via the package helper; MCP stdio fits Axiom MCP boundary) with PORT-CONCEPT for the receipt/obligation model and WorkPacket budgeting. Do not claim it powers lessons until a measured study on harder tasks exists.

## 5. ModelChecker (npm modelcheck-cli 0.2.0, MIT; repo root is a Next.js landing page + spec docs)
- What it does: CLI `modelcheck`. Two workflows: (a) capability suites (versioned core suite: structured_output 15 cases, tool_calling 15 cases) with deterministic scorers (JSON-schema via ajv, tool-call-match), per-case traceable report.json/html; (b) project regression: `init`, `baseline` (writes `modelcheck.lock`), `verify` (PASS/WARN/FAIL, exit codes for CI), `compare --candidate provider:model`; YAML config, JSONL cases, custom evaluators dir, `.modelcheck/runs/` private evidence. Adapters: OpenAI-compatible and Anthropic (so Ollama/llama.cpp OpenAI-compatible endpoints work via base_url, unverified). Repo-scan "recommend" and repo benchmark modules exist. Model-judged scoring is explicitly "designed, not built", always labelled and never mixed with deterministic aggregates. Also estimate (cost) and retry.
- Maturity: 40 commits 2026-09-18 to 2026-10-22, 74 test files, 131 tests reported passing offline (2026-09-19 report; count predates 0.2.0), one real-provider run verified, CI workflows, npm published 0.2.0. No server, no telemetry. Node>=20, deps only yaml + ajv.
- What it measures: whether a model/config change alters deterministic, assertion-checkable behavior (schema conformance, tool-call correctness, user-defined JSONL asserts). Not open-ended quality.
- Can it evaluate lessons/agents? Partly, and this is the best fit in the set. A "lesson" taught to a small model = prompt/skill + examples; baseline vs candidate (small model alone vs small model + lesson vs big model) is exactly `baseline`/`compare` with a lockfile as the regression gate, and Axiom's tool-calling/structured-output tasks (typed actions with argument schemas, S5) are exactly what its scorers check. Gaps: tool-calling scorer assumes OpenAI-style function tools, not multi-step agent trajectories or side-effect verification; no multi-turn/agent loop; no rubric judge yet; no per-lesson versioning concept.
- Interfaces: CLI, files (YAML, JSONL, lockfile, JSON/HTML report), CI exit codes. No daemon, no network except the model endpoint.
- Axiom view: (1) library/CLI used in CI and in a Developer Hub "Evaluate my agent/lesson" button; at runtime Axiom could run it on a local small model to gate lesson promotion ("lesson X may only be marked trusted if verify passes"). The file formats (JSONL cases, lockfile) can be adopted as the lesson eval format. (2) Needs: scorers, lockfile baseline, verdict semantics, denominator-honest reporting; duplicates: nothing in Axiom. (3) Cost: Node >=20, tiny deps; sends cases to a model endpoint (local OK); API key via env var only. Risk: scope is deterministic assertions only, so it may over-promise on "agent quality". (4) Verdict: BUNDLE as an optional dev/CI tool in the Developer Hub (small, dependency-light) and PORT-CONCEPT of its baseline/lock/compare discipline into Axiom's lessons pipeline. Strongest candidate for the evaluation harness; extend with trajectory and side-effect scorers rather than replace.

## 6. ContextGit (Python 0.2.0b6, Apache-2.0, same license as Axiom)
- What it does: (a) "git for LLM conversations": content-addressed immutable commits, mutable branch/HEAD pointers, merges that produce a summary commit, SQLite store, provider adapters, FastAPI HTTP/SSE + Typer CLI. (b) Multi-agent run management: one git worktree + branch per agent run under `<project>/.contextgit/worktrees` (WorktreeManager), per-run context branch, file-glob claims/ownership, status, integrate_run (merge code AND context together), merge queue, semantic cross-run conflict detection, merge agent. (c) Team mode: missions, tasks with roles/deps/scope/done_criteria/status (todo|blocked|working|review|done|failed), messages, events (audit), coordinator state machine with quality gates (tests/lint per worktree) and unblocking. Board is a file (`.contextgit/team.md`, mirrored into AGENTS.md managed block; this is exactly the "Parallel runs (managed by ContextGit)" block in Axiom's AGENTS.md) plus MCP stdio server `contextgit-mcp` (team_status, list_tasks, read_board, start_task, finish_task, post_update, check_ownership, peers, publish_contract, propose_team_plan, etc.; some tools orchestrator-only; run identity via CONTEXTGIT_RUN/TASK env). Launching a team writes `.mcp.json`. Electron desktop workbench with embedded terminals (pty) launching real agent CLIs (Codex, Claude Code, OpenCode...). Docs on code harness limits and run roles.
- Maturity: 200 commits (capped display), 2026-10-12 to 2026-10-25, ~23k LOC Python, 44 test files, e2e Playwright, CI + beta release workflow; beta, 0.2.0b6, not clear if on PyPI. Last commit 2026-10-25.
- Isolation answer: git worktrees + branches per run, claims as advisory file ownership (check_ownership/publish_contract; "stay inside files you own" is a prompt convention shown in AGENTS.md, enforcement level unverified: I saw no kernel-level sandbox, so isolation is VCS-level, not security-level), MCP board for coordination, merge queue to integrate. It does not sandbox processes, filesystems or network.
- Can it be Axiom's multi-session layer? As a concept yes, and the closest to the requirement "multi-session agent management". As the shipped component, only partially: it is git/code-project centric (worktrees need a git repo), whereas Axiom Jarvis sessions also cover non-code tasks and desktop actions. It also assumes agents are external CLIs in terminals rather than Axiom-defined agents with capability grants. It adds an HTTP server (FastAPI/uvicorn) and an Electron app (heavy) which clashes with the "no new daemon without ADR" rule; the MCP server alone is a per-session stdio process (acceptable). Security gap vs Axiom: no deny-by-default capability enforcement, runs agents with the user's full shell in terminals (the very pattern Axiom's rules forbid for AI).
- Axiom view: (1) Library + file format + MCP tool vocabulary. Port the data model (tasks, deps, claims, messages, events, contracts) into an Axiom session service; keep the board-file and MCP tool names for interop so external agent CLIs (Codex/Claude Code) in the Developer Hub can still join Axiom-managed sessions. Optionally bundle `contextgit-mcp` (stdio, Python) for the Developer Hub only. Context branching/merge (conversation version control) = the "memory/rollback" primitive for Jarvis; could back "never promise universal undo" with honest undo of conversation state. (2) Needs: worktree-per-run for coding agents, claims, board, quality-gate-before-merge, audit events; duplicates the LLM adapter layer, FastAPI API, Electron UI. (3) Cost: Python>=3.11 + pydantic + FastAPI + uvicorn (+ optional mcp) is acceptable (Axiom/Arch has Python anyway; unverified for the image), no root, local-first; risk is the HTTP API surface (bind to localhost only; unverified), worktree dirs inside user project, agents unsandboxed. (4) Verdict: PORT-CONCEPT for the session/board/claims/worktree model, with BUNDLE of just the stdio MCP + core library for coding sessions in the Developer Hub if a Phase 12 ADR approves it; do NOT bundle the Electron workbench or the FastAPI server as a resident daemon.

## Cross-repo picture
- aisskills (what agents may use, hashed and gated) + aiskills-library (content) + ModelChecker (does it work) + CodeAtlas (give small models good context, verify claims) + ContextGit (parallel sessions, ownership, audit) are complementary slices of the same Jarvis design. Overlap to resolve: skill registry (aisskills vs CodeAtlas Skills/tool registry), orchestration (aisskills CoreRuntime/Smurf vs ContextGit coordinator), MCP gateways (aisskills vs CodeAtlas vs ContextGit each run their own), sessions (CodeAtlas sessions vs ContextGit sessions). Axiom should pick one manifest format (aisskills' superset of Agent Skills) and one session model (ContextGit's task/board), and treat the rest as clients.
- Language mix: Node (3), Python (1) plus Electron: if Axiom ports concepts into one native service (Axiom services language), image weight stays small; bundling all four runtimes would not.

## Top 3 integration opportunities
1. Define Axiom agent/skill definition as an Agent Skills-compatible superset using aisskills' manifest (permissions, access, checks, risk_level) + lockfile with content/policy hashes + untrusted wrapper; seed with aiskills-library content.
2. Lessons pipeline gated by ModelChecker-style baseline/verify/compare: a lesson is promoted only if the small model + lesson beats the small model alone on deterministic cases (extend scorers for multi-step typed-action trajectories). CodeAtlas WorkPacket as the optional context scaffold for code lessons.
3. Multi-session layer modelled on ContextGit: worktree+branch per coding run, task graph with claims/contracts, board file + stdio MCP (compatible tool names so Codex/Claude Code can join), audit events, quality gate before integrate; context branches as honest conversation rollback.

## Top 3 risks
1. Isolation is not security: ContextGit claims/worktrees and aisskills guard (string-level, admits obfuscation misses) are advisory; adopting them as the boundary would violate Axiom's deny-by-default rule. Enforcement must be Axiom's typed broker + OS sandbox.
2. Runtime weight and daemon sprawl: Node 20/22 + native better-sqlite3/playwright, Python + FastAPI/uvicorn + Electron, WASM grammars; each repo runs its own MCP gateway/registry. Bundling all breaks the small-image and no-new-daemon rules (S9 needs an ADR).
3. Maturity and evidence gaps: all betas by one author, some unreleased or unpublished (CodeAtlas 0.7.0-beta.1 unpublished; aisskills latest features unreleased; library has 3 commits), small-model benefit unproven (CodeAtlas pilot is 48 runs, wide CIs, easy tasks), ModelChecker only covers deterministic structured-output/tool-call checks, and aisskills depends on an unlicensed Smurf and an external Warden binary.

Not checked: runtime behavior of any repo (read-only), npm/PyPI publication status, Warden/ShieldCI internals, whether ContextGit enforces claims in code, image size numbers, CodeAtlas-ui license intent.
